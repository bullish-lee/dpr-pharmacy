> 버전 0.1 (초안) · 2026-11-17 · 대상 독자: 개발자(유지보수), 약사(업무 흐름 확인)

## 1. 목표와 범위

### 1.1 해결하려는 문제
급여 의약품은 국가가 정한 상한금액으로만 거래된다. 보건복지부가 「약제 급여 목록 및 급여 상한금액표」를 매달(때로는 월 2회) 개정하며 가격을 내리면, 약국이 이미 비싸게 사 둔 재고에서 손실이 생긴다. 도매는 두 방식으로 차액을 보상한다.

| 방식 | 내용 | 보상액 |
|---|---|---|
| **서류보상** | 도매가 '최근 N개월 사입량 × 비율(보통 30%)'만큼 원장에서 반품·재사입 처리 | 서류보상수량 × 1단위 인하폭 (보유량과 무관) |
| **실물보상** | 약국이 보유한 실물의 바코드를 도매 앱에 등록 | 등록 수량 × 1단위 인하폭 |

두 방식은 **(약품, 도매) 단위 택일**이다. 약국은 매 인하마다 품목·도매별로 어느 쪽이 유리한지 따져야 하지만, 품목 수가 많고(한 번에 수천 품목까지) 도매별 기준이 제각각이라 대부분 포기하고 손실을 떠안는다.

### 1.2 목표 (기획서 a~h단계)
1. 복지부 고시를 **하루 2~3회 자동 확인**해 신설·삭제(구분 표시)와 변경(인하·인상·제품명·약가유연계약)을 정리한다.
2. 이팜(eFarm) 엑셀로 **추정재고**(초기재고 + 사입 − 조제)를 계산하고, 실계수를 입력하면 실계수를 우선한다.
3. **손실이 큰 순서**로 품목을 보여준다. 손실은 (현재 매입가 − 인하 후 상한금액) × 재고다.
4. 도매별 기준으로 **서류보상 수량**을 계산해 품목·도매별로 **서류/실물 판정**을 한다.
5. 실물보상 후보는 **바코드**로 사입 도매를 확인한다. 바코드의 제조번호·유효기간을 사입 근거와 대조하고, 여러 도매에 걸리면 '확인 필요'로 표시한다.
6. **도매 앱 등록을 돕는다.** 바코드를 화면에 한 개씩 크게 다시 그려 휴대폰 도매 앱으로 찍게 하고, 스캔완료를 체크한다.
7. 처리 결과(어느 약·어느 도매·몇 개·얼마)를 저장하고 집계한다.

### 1.3 비목표 (초안 범위 밖)
- 도매 앱·도매 원장과의 직접 연동: 공개 API가 없다.
- 공동인증서 로그인이 필요한 요양기관업무포털 자동 접속. 해당 자료는 약사가 내려받은 파일을 가져오는 방식만 지원한다.
- 환자 정보 처리. 조제현황은 '환자정보 삭제본'만 사용한다.

### 1.4 비기능 요구사항 → 설계 대응
| 요구 | 대응 |
|---|---|
| 저지연·빠름 | 엑셀은 가져올 때 1회만 읽어 SQLite에 적재하고, 화면 조회는 인덱스 SQL로 처리. 심평원 표준코드(약 30만 행)도 몇 초 안에 읽는다. 바코드 판독은 앱 안 WASM으로 처리(서버 왕복 없음). |
| 저부하 | Go 단일 프로세스 + 내장 SQLite, 상주 메모리는 수십 MB. 바코드 엔진(WASM)은 스캔 화면을 열 때만 로드. |
| 안정성 | 정수 고정소수 수량(부동소수 반올림 오류 제거), 트랜잭션 단위 가져오기, WAL, 하루 1회 자동 백업(30개 보관), 단일 실행 잠금, 수집 중복 실행 방지, 실데이터 회귀 테스트. |
| 수정 용이 | 계층 분리(domain은 순수 함수), 도매 기준은 코드가 아닌 데이터(화면에서 수정·버전 관리), 엑셀 양식은 동의어 + 사용자 매핑으로 처리(코드에 열 위치 고정 없음). |
| 배포 편의 | Windows용 단일 실행 파일 `DPR.exe`(약 23MB, 설치·런타임 불필요, Mac에서 교차 빌드). 데이터 폴더는 별도라 exe만 교체하면 업데이트된다. |
| UI/UX | 리서치 기반 디자인 토큰(docs/UI_GUIDE.md), 표 중심의 고밀도 화면, 조치가 필요한 곳에만 색 사용, 키보드 우선 조작. |
| 오픈소스 대비 | 약국별 정보(도매명 등)를 코드에 하드코딩하지 않음, 허용적 라이선스 의존성만 사용, 테스트와 문서 포함. |

## 2. 용어

| 용어 | 정의 |
|---|---|
| 보험코드(제품코드, EDI) | 9자리 약품 코드. 고시와 매칭하는 키. 엑셀이 숫자로 저장하며 앞 0이 사라진 8자리는 9자리로 복원한다. 7자리는 이팜 내부코드(비급여)다. |
| 표준코드(GTIN) | 포장 바코드의 13자리(880…), GS1 AI(01)에서는 앞에 0을 붙인 14자리 |
| 상한금액 | 고시 단위(정·캡슐·관·병 등) 1개당 급여 상한가 |
| 시행일 | 고시 변경이 효력을 갖는 날. 한 고시 안에서도 시트별로 다를 수 있다(예: 26.11.01 / 26.11.11 / 27.11.11). |
| 유예(경과조치) | 삭제 품목이 급여를 유지하는 기한(예: ~'27.04.30) |
| 기준점(anchor) | 재고를 확정한 시점과 수량. 초기재고(initial) 또는 실계수(count) |
| 시점(timing) | 기준점이 그날 거래의 '영업 전'(start)인지 '영업 후'(end)인지 |
| 대상기간(window) | 서류보상 수량을 셀 사입 기간 |
| 회차(case) | 하나의 시행일에 대한 대응 작업 단위 |
| 약가유연계약 | 고시에는 표시가만 있고 실제 상한금액(별도합의)은 업무포털에서만 확인 가능한 품목 |

## 3. 입력 파일 구조 (설계 근거)

| 파일 | 구조 | 특이사항 |
|---|---|---|
| 사입현황 | 제목행 `사입현황 YYYYMMDD ~ YYYYMMDD` + 헤더(일자·약품명·약품코드·거래처·구분·단위·단위수량·수량·단가·합계·재고단위·재고수량·제약회사) | 단가 = **포장 단가**. 1단위 단가 = 단가 ÷ 단위수량. 반품·폐기·차용출고는 수량이 음수. `재고수량` 열은 일관성이 없어 쓰지 않는다. 유효기간·제조번호 열 없음 |
| 조제현황 | 일자·약품명·약품코드·단위·단위수량·투약량·일수·횟수·총수량 | `총수량`이 기준(투약량×일수×횟수와 다른 행이 있음). 0.5정 등 소수 수량 존재 |
| 초기재고 | 시트마다 양식이 다를 수 있음(보관 위치·포장별로 나눈 시트 등) | 코드 없이 이름만 있는 시트, 포장 단위('30T × 6통') 표기, 숫자로 저장돼 앞 0이 사라진 코드 |
| 고시 목록표 | 별지(신설·변경·삭제, 시트명에 시행일·유예), 변경대비표(변경 전/후·비고·시행일) | 변경 품목은 별지에 '변경 후'만 있고 변경 전은 대비표에 있다. 비고에 상한금액/인상/제품명/별도합의금액 구분 |

**계산 예 (합성 수치)**
- 재고: 초기 200 + 사입 1,000 − 조제 800 = **400정**. 인하폭 20원이면 손실 8,000원.
- 3개월 30% 서류보상: 가람 240 + 나래 120 + 다솜 60 = **420 ≥ 400 → 서류보상**.

```

[수동] 이팜 엑셀 업로드(초기재고·사입·조제·제조번호 사입근거·표준코드 매핑)

          ▼

                                                         │
                                                         ▼
                                     품목 판정(도매별 서류보상·보유·방식, 근거 문장)

                                         ▼                       ▼
                               바코드 스캔(도매 매칭)     판정 확정 → 처리 예정

                                         ▼
```

| a 재고 | 데이터 가져오기, 재고 | 초기재고(기준일 지정·언제든 수정), 사입·조제 범위 교체, 실계수 |

## 5. 아키텍처

### 5.1 형태
**로컬 데스크탑 앱**(Go + Wails v2)이다. 결과물은 `DPR.exe` 하나이며, 화면은 Windows 내장 WebView2가 그리는 React UI다. 인터넷은 고시를 수집할 때만 쓴다. 같은 exe를 `DPR.exe crawl`로 실행하면 창 없이 수집만 하므로 Windows 작업 스케줄러에 등록해 쓴다. 앱이 꺼져 있어도 하루 3회 수집된다.

### 5.2 계층 (의존 방향은 위 → 아래만)
```
frontend/ (React+TS)  ──Wails 바인딩──▶  app.go (얇은 어댑터) / cli.go (명령줄)
                                            │
                                   internal/service   유스케이스 조립 (DB+파서+계산+수집기)
                                   ├── internal/ingest   스키마·헤더 탐지·열 매핑·레코드/고시 파서
                                   ├── internal/sheet    xlsx(원본값)/CSV(UTF-8·CP949) 리더
                                   ├── internal/crawler  복지부 RSS·첨부 수집
                                   ├── internal/store    SQLite(WAL)·내장 마이그레이션·백업
                                   ├── internal/platform OS 기능(작업 스케줄러·토스트·폴더)
                                   └── internal/domain   순수 계산 (I/O 없음, 테스트 쉬움)
```

### 5.3 기술 선택
| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 셸 | Wails v2.17 | 단일 exe, WebView2(Win10/11 기본 탑재), Go↔JS 바인딩 자동 생성 |
| DB | SQLite — C SQLite(mattn/go-sqlite3, cgo) 기본, 순수 Go(modernc) 대체 | 실데이터에서 C SQLite 가 조회 약 2배 빠름(재고 계산 60→29ms). 맥에서 mingw-w64 로 Windows exe 교차 빌드(UCRT 외 DLL 의존 없음), cgo 가 없으면 자동으로 순수 Go 빌드. 파일 1개, WAL로 읽기·쓰기 동시 |
| 엑셀 | 전용 xlsx 리더(시트 XML 직접 읽기, 큰 시트는 병렬) + excelize v2 대체 | excelize 대비 5~9배 빠름, 결과는 실파일 전부에서 셀 단위로 같음. 셀 서식 대신 원본 값 → 코드 앞 0·날짜 일련번호를 직접 해석 |
| 바코드 판독 | zxing-wasm 3 (reader, 로컬 WASM) | zxing-cpp 엔진, 저해상도 사진에서도 GS1 DataMatrix 판독(실측) |
| 바코드 생성 | bwip-js 4 (gs1datamatrix) | FNC1·GS1 검증 내장, SVG라 화면 배율과 무관하게 선명 |
| UI | React 19 + TS + Tailwind v4 + TanStack Query/Virtual | 로컬 앱 맞춤 쿼리(networkMode always), 수천 행 가상 스크롤 |
| 글꼴 | Pretendard Variable (앱 내장) | 오프라인, 한글 가독성 |

## 6. 데이터 모델 (SQLite)

마이그레이션은 `internal/store/migrations/*.sql`을 실행 파일에 내장하고 `PRAGMA user_version`으로 관리한다. 마이그레이션은 **추가만** 한다(표·열을 지우거나 이름을 바꾸지 않음, `TestMigrationsAreAdditive`) — 업데이트 뒤 `DPR.exe.old`로 되돌려도 옛 exe 가 새 DB 를 그대로 쓴다. 규칙은 다음과 같다.
- 날짜는 `YYYY-MM-DD` 텍스트로 저장한다.
- 수량은 **1/1000 단위 정수**(qty)로 저장한다.
- 금액·단가는 REAL(원)로 저장한다.

| 테이블 | 용도 | 핵심 컬럼 |
|---|---|---|
| product | 약품 마스터(자동 수집) | code, name, stock_unit, pack_size(바코드 1개 = 낱개 수), unit_factor(재고↔고시 단위 배율, 사용자 지정) |
| supplier / supplier_alias | 거래처, 원본 표기 별칭 | kind(wholesaler/other), active, deleted(사용 이력 있으면 숨김) |
| comp_rule | 도매별 보상 기준(버전) | supplier_id(NULL = 기본 규칙), valid_from, rate_bp, window_mode, lookback, cutoff_day, extend_to_anchor, anchor, rounding, net_returns, settlement_day, needs_review |
| import_batch / import_profile | 가져오기 이력, 사용자 열 매핑(양식 서명) | range_from/to, summary / signature, mapping |
| purchase_line | 사입(부호 포함) | date, product_code, supplier_id, kind, qty, unit_price, lot, expiry |
| dispense_line | 조제 | date, product_code, qty |
| stock_anchor | 재고 기준점 | as_of, timing(start/end), qty, source(initial/count), unit_price |
| initial_unresolved | 초기재고 중 코드 미확정 행 | name, qty, candidates(JSON), resolved_code, ignored |
| notice / price_change | 고시, 품목별 변동 | kind(new/change/delete), detail(price_down/up/agreed_price/name_change…), price_before/after, before_source, effective_date, grace_until, flexible |
| lot_evidence | 제조번호 사입 근거 | supplier_id, lot, expiry, qty, source(import/manual/photo) |
| gtin_map | GTIN → 보험코드 | source(official/user/heuristic), pack_qty(제품총수량), name |
| scan_unit | 스캔한 실물 | effective_date, gtin, lot, expiry, serial(회차 내 유일), qty, match_status, candidates, supplier_id, resolved_by, registered |
| window_override | 회차별 대상기간 직접 지정 | effective_date, supplier_id, from, to |
| settlement | 처리 결과 | (시행일, 약품, 도매) 유일, method, qty, unit_delta, amount, status(planned/done), rule_snapshot(JSON) |
| job_run / notification / app_setting | 수집 기록, 알림, 설정 | |

**가져오기 멱등성**
- 사입·조제는 파일 제목(또는 최소~최대 일자)의 **기간을 통째로 교체**한다. 같은 기간을 다시 올려도 중복되지 않고, 수정분이 반영된다.
- 고시는 파일 SHA-256으로 중복을 막는다.

## 7. 핵심 알고리즘

### 7.1 추정재고
```
재고(시점 T) = 최신 기준점 수량 + Σ 사입(기준점 이후 ~ T, 부호 포함) − Σ 조제(기준점 이후 ~ T)
```
**기준점 선택**
- as_of ≤ T인 기준점 중 가장 늦은 것을 쓴다. 같은 날이면 영업 후(end)를, 그다음 실계수를 우선한다.
- 기준점이 없는 품목은 '초기재고 기준일에 0개'로 본다. 초기재고 파일은 기준일 시점의 전체 목록이기 때문이다.

**당일 반영 규칙**
- 기준점이 '영업 전'이면 기준일 당일 거래부터 반영한다.
- '영업 후'면 다음 날부터 반영한다.

**계산 시점과 표시**
- 지난 시행일은 '시행 전날' 재고로, 다가오는 시행일은 '오늘' 재고로 분석한다.
- 화면에는 실계수를 무시한 **추정재고**와 실계수를 반영한 **최종 재고**를 함께 보여준다.

**구현:** 약국 한 곳의 품목 수(수천 개) 기준으로 인덱스 (product_code, date)의 상관 서브쿼리 SQL 1회로 계산한다.

### 7.2 단위 체계 · 현재가 · 인하폭

**모든 수량은 '고시 단위'로 센다.** 고시 단위는 급여목록의 상한금액이 매겨진 단위(규격 + 단위 열)이고, 이팜 조제 '총수량'(청구 수량)과 같다.

- **근거 (공식):** 「약제 급여 목록 및 급여 상한금액표」 제2조④⑤
  - "모든 약제는 정, 캡슐, 앰플, 병, 통 등 생산규격단위로 등재"
  - "분할조제용 내복제 등은 규격란에 "(1)"로 구분하여 최소단위 가격을 표기"
  - 심평원 청구 작성요령도 팩 단위 약(예: 21정/팩)을 팩 단위로 청구한다.
- **근거:** 이팜 조제의 '단위·단위수량'은 급여목록 규격과 일치한다.

| 규격 · 단위 | 의미 | 고시 단위 |
|---|---|---|
| `1` · `정` | 1정당 가격 | 정 |
| `28` · `정/팩` | 28정 든 1팩당 가격 | 팩(28정) |
| `0.4` · `mL/관` | 0.4mL 1관당 가격 | 관(0.4mL) |
| `100(1)` · `g/통` | 100g 통, 1g당 가격(분할조제용) | g (1통 = 100g) |

- **사입·초기재고 환산:**
  - 이팜 사입은 약품 설정에 따라 원본 단위가 섞여 있다. 예: 28정 1팩 약을 '정'으로, 100g 통을 '통'으로, 100정 1통을 '1'(단위수량 오기)로 기록한다.
  - 그래서 원본을 보관하고, 배율(원본 1단위 = 고시 단위 N개)을 곱해 저장한다.
  - 배율은 품목 × (이팜 단위, 단위수량) 묶음마다 `원본 1단위 단가 ÷ 그 시점 상한금액`의 중앙값으로 정한다. 매입가는 대부분 상한금액 근처다.

| 단가 비율 | 판단 | 상태 |
|---|---|---|
| 0.65~1.55 | 같은 단위 → 배율 1 | ok |
| 고시 구조가 설명하는 값 근처 (`N(1)` → N, N개들이 → 1/N) | 그 배율 | auto_unit (단위 환산) |
| 정수 k(≥2)에 3% 이내이고, k가 표준코드 포장 수량이거나 10 이상 | k (단위수량 오기 보정) | auto_pack |
| 그 외 | 배율 1, 매입가 대신 고시 가격 차이로 손실 계산 | check (단위 확인) |

- **단가 근거가 없는 기록** (반품·폐기만 있는 묶음, 단가 없는 초기재고·실사 행):
  1. 같은 단위 이름(정=T, 캡슐=캅셀 등 표기 차이는 맞춤)의 사입 판단을 따른다. 원본 수량은 그 단위의 낱개라 단위수량이 달라도 배율이 같다. 단, 단위수량 오기 보정(auto_pack)은 그 묶음에만 맞으므로 물려주지 않는다.
  2. 단위 이름이 고시 단위 자체면 배율 1.
  3. 그 외에는 다른 단위 묶음의 배율을 짐작해 곱하지 않고 배율 1 + **확인 필요**로 드러낸다.
- **실사 파일:** 초기재고와 같은 규칙으로 환산한다(`count_line`, 기준 가격 = 실사일 고시 가격). 실사 기준점 수량 = 행 합계. 손으로 넣는 실계수는 입력할 때 단위를 고른다.
- **다시 계산하는 때:** 급여목록·고시·표준코드·사용자 지정·기준일이 바뀔 때, 가져오기를 지우거나 같은 기간을 새 파일로 바꿀 때, 고시를 다시 해석하거나 지울 때. 묶음을 정렬해 판단하므로 가져오는 순서·읽는 순서와 결과가 무관하다(실데이터로 두 순서를 비교해 검증, 이름 매칭 2건만 차이).
- **같은 품목·시행일에 고시가 여럿이면:** 가격을 말하는 고시(인하·인상·변경없음·유연계약) 중 가장 최근 게시된 것이 정한다 — 정정 고시(변경 없음)가 앞선 인하를 취소한다. 제품명 변경 등은 앞선 인하를 취소하지 않는다. 변경 후 가격을 읽지 못한 인하(빈칸)는 손실 0 + 실제가 확인.
- **급여목록표:** 심평원 「약제급여목록 및 급여상한금액표」(월별 전체, 공개용)를 가져오면 모든 품목의 고시 단위를 안다. 없으면 고시에 나온 품목만 판단한다.
- **바코드 1개:** 표준코드의 '제품총수량'(단위 = 제형구분: 정·캡슐·개·포·관 …)을 고시 단위로 바꾼다(28정 PTP → 1팩, 100g 1병 → 100g, 10mL 50포 → 500mL). 우선순위는 사용자 지정 → 표준코드 → 사입 포장 환산이다.
- **현재가 우선순위:** 시행일 전 마지막 사입의 고시 단위 단가 → 초기재고 단가 → 고시 변경 전 가격. 단위 확인(check) 품목은 고시 변경 전 가격을 쓴다.
- **인하폭:** 현재가 − 인하 후 상한금액. 음수면 0이다.
- **약가유연계약:** 표시가로는 손실을 계산하지 않고 '실제가 확인 필요'로 분리한다(합계에서 제외).
- **실물보상과 개봉품:** 업계 관행상 실물(반품) 보상은 그 도매가 공급한 같은 제조번호·유효기간의 미개봉 포장만 받는다. 소분·낱알·ATC 투입분은 받지 않는다. 그래서 실물 보유 수량은 바코드 스캔(포장 단위)을 기준으로 하고, 스캔 전 추정치에는 개봉품이 섞여 있을 수 있다. 서류(자동)보상은 사입 수량 기준이라 개봉 여부와 무관하다.

### 7.2.1 데이터 점검 · 화면 속도

  - 자동 환산
  - 급여목록 없음·40일 넘음, 받지 못한 고시
- **계산 캐시** (`internal/service/cache.go`)
  - 대상: 재고·단가·품목 요약·점검 결과
  - 무효화: 'PRAGMA data_version' 전용 연결. 다른 연결(이 앱의 모든 쓰기, 다른 프로세스)이 커밋하면 다음 조회에서 다시 계산한다. 계산 중에 데이터가 바뀌면 다음 조회에서 버전이 달라 다시 계산한다(옛 결과를 보여 주지 않는다).

  - 부분 색인 `ix_purchase_price`: 마지막 사입 단가

### 7.3 서류보상 대상기간 (도매별 규칙)
| 방식 | 계산 | 예 (시행 2026-11-01) |
|---|---|---|
| cycle, 마감일 말일 (=달력 월) | 기준일 이전 마지막 마감일부터 N개월 | 3개월 → 08-01 ~ 10-31 |
| cycle, 마감일 15일 | 16일~다음달 15일 주기 N개 | 2주기 → 08-16 ~ 10-15 |
| cycle + extend_to_anchor | 위 기간에 마감 후 ~ 기준일 전날 포함 | 08-16 ~ 10-31 |
| rolling_month | 기준일 직전 N개월 | 11/20 시행·2개월 → 09-20 ~ 11-19 |
| rolling_day | 기준일 직전 N일 | 60일 → 09-02 ~ 10-31 |

- 기준일은 시행일 또는 고시일 중에서 고른다.
- 회차마다 도매별 기간을 직접 지정할 수 있다(window_override).
- 결제일(정산일)은 안내용이며, 결제 예정일을 계산해 보여준다.

### 7.4 서류보상 수량
```
기준량 = 기간 사입 − (반품 차감이면) 기간 반품      (양수만)
서류보상수량 = 반올림방식(기준량 × 비율)              (정수 연산: 90 × 30% = 정확히 27)
```

### 7.5 판정
- **품목 단위** (기획서 규칙):
  - 재고 ≤ 서류보상 합계이면 **서류보상**(바코드 작업 불필요).
  - 재고 > 서류보상 합계이면 **실물보상 검토**.
- **도매 단위:** 보유량 > 서류보상수량이면 실물, 아니면 서류(택일). 보유량은 다음 순서로 정한다.
  - 바코드 스캔 결과가 있으면 그것을 쓴다.
  - 없으면 **FIFO 추정**을 쓴다. 최근 사입분부터 남아 있다고 가정해 도매별로 배분한다.
- **예상 보상 = Σ max(서류보상수량, 보유량) × 인하폭.** 서류보상은 보유와 무관한 고정 크레딧이므로 합계가 재고를 넘을 수 있다(순손실이 음수면 이득).
- **실물 추가 이익:** 품목 판정이 '서류보상'이어도 도매별로 실물이 유리한 경우가 있다. 이때 '실물 +n'으로 표시한다(예: 도매 두 곳에서 실물이 더 많으면 그 차이만큼 +n).

### 7.6 바코드 → 약품 → 도매
1. **GS1 파싱.** 입력은 괄호 표기, GS(0x1D) 원문, `]d2` 접두, 스캐너가 바꿔 보낸 대체 구분자(~ | ^)를 모두 받는다. 유효기간 DD=00이면 그 달 말일로 본다.
2. **GTIN → 보험코드.** 다음 순서로 찾고, 처음 보는 GTIN은 사용자가 한 번 지정하면 학습한다.
   - 공식 매핑: 심평원 약가마스터
   - 사용자 확정 매핑
   - 추정 규칙: 표준코드 4~11번째 자리 = 보험코드 앞 8자리, 후보가 여럿이면 EAN 12번째 = 보험코드 9번째로 좁힘
3. **도매 매칭.** 제조번호(+유효기간)를 사입 근거와 대조한다. 사입 근거는 사입현황의 제조번호 열과 별도 근거를 합친 것이다.
   - 한 곳이면 자동 귀속
   - 여러 곳이면 '확인 필요'(사용자가 도매 앱에서 확인 후 번호로 지정)
   - 없으면 '매칭 없음'
4. **중복 처리.** (시행일, GTIN, 일련번호)가 같으면 중복으로 보고 집계하지 않는다. 다른 약품의 바코드는 경고한다.

### 7.7 고시 해석
- **시트 역할**은 키워드로 판별한다. 붙임을 먼저 판별해야 '…금번신설…' 오인을 막는다.
- **시행일·유예**는 시트명 정규식에서 읽는다.
- **변경 품목**은 변경대비표와 시행일이 같은 행을 결합해 다음 중 하나로 분류한다: 인하, 인상, 동일, 제품명, 별도합의(유연계약).
- **변경 전 가격**이 없으면 과거 고시 이력, 그다음 최근 사입가 순으로 보완한다(출처를 before_source에 기록).

- 3일 넘게 성공 기록이 없으면 경고한다. RSS가 30건만 보여주므로 오래 꺼져 있으면 고시를 놓칠 수 있기 때문이다.
- 앱 내 스케줄러와 작업 스케줄러가 동시에 돌지 않도록 막는다. DB의 running 기록(작업마다 같은 '멈춤' 시간 — 고시 10분·표준코드·급여목록 30분, 각 작업의 시간 한도보다 김)과 분석 완료 상태를 이 용도로 보호한다.
- 작업 스케줄러를 등록해도 앱 안 확인은 계속한다(등록이 깨져도 확인이 멈추지 않게). 같은 시각에 겹치면 하나만 돌고, 10분 안에 한 고시 확인은 건너뛴다.
- 앱은 30초마다 `PRAGMA data_version`을 보고 다른 프로세스(작업 스케줄러)가 쓴 것이 있으면 화면을 새로 고친다.

**실측:** 실제 RSS → 제2026-219호 자동 수집·분석을 확인했고, 원본 해시도 일치했다.

## 10. 안정성 · 보안 · 개인정보

**데이터**
- **저장 위치:** `DPR_DATA_DIR` → exe 옆 `dpr-data`(휴대용) → 위치 기록 `DPR-data-location.txt`(기본 폴더 **옆**, `%APPDATA%\DPR-data-location.txt`)이 가리키는 폴더(설정에서 옮긴 경우; v0.2.1 까지의 `%APPDATA%\DPR\data-location.txt` 도 읽고 다음 기록 때 옮김) → `%APPDATA%\DPR`(Windows)·`~/Library/Application Support/DPR`(macOS). 위치 기록을 기본 폴더 밖에 두어, 옮긴 뒤 원래 폴더를 지워도 빈 자료로 열리지 않는다. 옮긴 폴더를 찾지 못하면 앱·작업 스케줄러 모두 시작하지 않는다(빈 자료로 열어 자료가 갈라지지 않게).
- **옮기기:** 작업(가져오기·고시·표준코드·급여목록·업데이트)이 없을 때만, 화면을 막은 채로: 기록·원본·보고서 복사(오래 걸림) → 한 연결로 `PRAGMA data_version` → 수정 기록 → 사본(VACUUM INTO) → 사본 확인(스키마·행 수·quick_check) → data_version 이 그대로인지(다른 연결·작업 스케줄러가 썼으면 취소) → 위치 기록 → 다시 시작. 다시 시작하지 못하면 위치 기록을 되돌린다. 원래 폴더는 남긴다. 네트워크 폴더(UNC·네트워크 드라이브)는 데이터 폴더로 고를 수 없다(SQLite WAL 은 네트워크 파일 시스템에서 안전하지 않음). DB 경로의 `%`·`#`·`?` 는 file: URI 에서 이스케이프한다.
- **백업 폴더:** 따로 정할 수 있고, 쓸 수 없으면 기본 위치에 백업하며 장애마다 한 번 알린다.
- **외부 전송 없음:** 인터넷은 복지부 고시 수집, 심평원 표준코드 새 판 확인, GitHub 새 버전 확인, (사용자가 누를 때) 오류 보고에만 쓴다. 약국 거래 자료는 보내지 않는다. 실제 약국 데이터는 저장소에 커밋하지 않는다(`.gitignore`).

**안정성**
- 모든 가져오기는 하나의 트랜잭션으로 처리한다(실패·패닉 시 전체 취소, 쓰기 잠금도 풀림).
- 기간 교체 안전장치: 같은 기간 기존 기록보다 약품 수가 크게 적거나(20% 미만), 기존 기록의 도매처가 새 파일에 통째로 없으면 먼저 확인한다. 시트마다 기간을 나눠 교체한다(1월·3월 시트가 2월을 지우지 않음).
- 엑셀 읽기는 행 1,048,576 · 열 16,384 · 시트 512MB 한도를 넘으면 오류로 끝낸다(망가진 파일로 앱이 멈추거나 죽지 않게).
- 수집·표준코드 작업은 '실행 중' 확인과 기록을 한 문장으로 해 앱과 작업 스케줄러가 동시에 돌지 않는다. 앱 종료로 중단된 수집은 실패로 세지 않는다.
- 하루 1회 `VACUUM INTO`로 백업하고, 백업은 30개까지 보관한다.
- 로그는 `data/logs/dpr.log`에 남기고 5MB가 넘으면 회전한다.
- 단일 실행 잠금을 건다. 두 번째로 실행하면 기존 창을 앞으로 가져온다.

**보안**
- 오류 보고는 기록에서 토큰·데이터/홈 폴더·드라이브 경로(공백·역슬래시 두 번 형태 포함)·엑셀/CSV 파일 이름을 가린 뒤 보낸다. 약국 거래 자료는 넣지 않는다.
- 업데이트 파일은 체크섬과 개발자 ed25519 서명(버전·파일 이름·SHA-256 을 묶어 서명)이 모두 맞을 때만 설치한다([RELEASING.md](RELEASING.md)).
- 업무포털 공동인증서 로그인은 자동화하지 않는다.
- 약가유연계약 실제가는 앱 밖으로 내보내지 않는다(향후 가져오기 기능에도 적용).

## 12. 확장 지점 (오픈소스·다른 약국 대응)
- **다른 약국 프로그램(유팜·PM+20 등) 양식:** 스키마 동의어를 추가하거나 사용자 매핑을 저장한다(코드 수정 최소).
- **새 도매 기준:** 데이터로 처리한다. 방식이 더 필요하면 `domain.CompRule` + `CompWindow`만 확장한다.
- **로드맵 항목:** 심평원 월별 전체 약가표(변경 전 가격·집행정지), 업무포털 입고조회·사전가중평균가(도매별 공급 공식 기록), 자동 업데이트.
