# 릴리스 만들기 · 서명 키

> 개발자용입니다. 약국에서 쓰는 사용법은 [RELEASE_README.txt](RELEASE_README.txt)에 있습니다.

## 왜 서명하나

앱은 켤 때 GitHub 릴리스를 확인하고, 새 버전을 받아 **실행 파일을 바꿉니다**. 그래서 릴리스를 올릴 수 있는 사람은 약국 PC에서 프로그램을 실행할 수 있는 셈입니다.

| 확인 | 막는 것 | 못 막는 것 |
|---|---|---|
| `.sha256` (같은 릴리스에 들어 있음) | 받다가 깨진 파일 | 저장소 쓰기 권한이 있는 사람(유출된 토큰 포함)이 올린 파일 |
| `.sig` (개발자 비밀 키로 서명) | 위의 모든 경우, 옛 버전 파일을 새 버전인 척 올리기 | 비밀 키 자체의 유출, 저장소에 몰래 들어간 코드 |

동작은 이렇습니다.
- 앱에는 공개 키만 들어 있습니다(`internal/updater/keys.go`).
- 새 버전을 **알리기 전에** 작은 `.sig` 파일을 받아 서명부터 확인합니다. 서명이 없거나 맞지 않는 릴리스는 이름조차 화면에 띄우지 않습니다.
- 설치할 때 zip까지 받아 한 번 더 확인합니다. 사용자가 확인한 버전과 지금 최신이 다르면 설치하지 않습니다.
- 서명하는 내용은 **버전 + 파일 이름 + zip의 SHA-256**입니다. 옛 버전 zip을 새 버전 번호로 다시 올려도 설치하지 않습니다.

## 비밀 키 · 허용 목록

| 파일 | 내용 |
|---|---|
| `~/.config/dpr/release-signing.key` | 비밀 키 (권한 600). 공개 키 ID `6aa440c9dc8e78e0` (2026-11-18) |
| `~/.config/dpr/trusted-keys` | 앱에 넣어도 되는 공개 키 목록. **저장소 밖**에 둡니다 |

- **허용 목록이 하는 일:** `make release`는 앱에 든 공개 키가 모두 이 목록에 있는지 확인합니다. 저장소에 쓰기 권한이 있는 다른 사람이 `keys.go`에 자기 키를 한 줄 넣으면, 그 사람이 다음부터 업데이트를 서명할 수 있게 됩니다. 이 확인으로 그런 변경이 릴리스에 섞이지 않습니다.
- 두 파일 모두 **저장소·이슈·메신저에 절대 올리지 않습니다.**
- **백업:** 비밀번호 관리자나 암호화한 USB에 한 부를 따로 보관하세요. 키를 잃으면 자동 업데이트를 할 수 없고, 새 키를 넣은 버전을 각 약국에 한 번 직접 설치해야 합니다.
- **백업에서 되살릴 때:** 키 파일을 제자리에 두고 `go run ./tools/relsign trust`를 실행합니다. 비밀 키에서 공개 키를 직접 구해 허용 목록에 넣습니다.
- **유출이 의심되면:** 아래 '키 바꾸기'를 바로 하고, GitHub 토큰도 모두 다시 발급합니다.

## 릴리스 순서

1. `VERSION` 파일의 버전을 올리고 커밋합니다.
2. `make release`를 실행합니다. 다음이 한 번에 진행됩니다.
   1. **점검:** 커밋하지 않은 변경이 있으면 멈춥니다. 허용 목록을 확인하고, 지난 릴리스 뒤 바뀐 업데이트·빌드 관련 파일의 커밋을 보여 줍니다.
      - 대상 파일: updater, relsign, Makefile, app.go, main.go, package.json, package-lock.json, vite.config.ts, go.mod, go.sum
   2. **모두 직접 한 변경인지 읽어 봅니다.** 저장소에 몰래 들어간 코드는 서명이 막지 못합니다.
   3. Windows exe를 빌드하고 zip으로 묶습니다.
   4. relsign이 `.sha256`과 `.sig`를 만듭니다.
   5. 앱과 같은 방법으로 확인합니다. 확인에 실패하면 멈춥니다.
3. wails.json 버전 표시를 커밋합니다. 태그를 **이 PC에서** 달고 올린 뒤 GitHub 릴리스를 만듭니다. 자산 3개를 모두 올립니다.
   - 태그를 GitHub에서만 만들면 다음 점검에서 '지난 릴리스'를 찾지 못합니다.
   ```sh
   git tag v$(cat VERSION) && git push origin v$(cat VERSION)
   gh release create v$(cat VERSION) build/release/DPR-v$(cat VERSION)-windows.zip{,.sha256,.sig} --verify-tag --title "v$(cat VERSION)" --notes-file <노트>
   ```
4. 올린 뒤 받은 파일로 한 번 더 확인합니다.
   ```sh
   gh release download v$(cat VERSION) -D /tmp/rel
   go run ./tools/relsign verify -version $(cat VERSION) /tmp/rel/DPR-v$(cat VERSION)-windows.zip
   ```

## 키 바꾸기

일정 기간 **두 키로 함께 서명**해서, 중간 릴리스를 놓친 약국도 넘어갈 수 있게 합니다.

1. 새 키를 다른 경로에 만듭니다.
   ```sh
   DPR_SIGNING_KEY=~/.config/dpr/release-signing-2027.key go run ./tools/relsign keygen
   ```
   새 공개 키가 허용 목록에 자동으로 추가됩니다.
2. 출력된 새 공개 키를 `TrustedKeys`에 **추가**합니다. 옛 키는 그대로 두고, `TestEmbeddedKeysArePinned`의 키 ID도 고칩니다.
3. 몇 달 동안은 두 키로 서명합니다. 옛 키만 아는 앱도, 새 키만 아는 앱도 받아들입니다.
   ```sh
   DPR_SIGNING_KEY=<옛 키>:<새 키> make release
   ```
4. 모든 약국이 새 버전으로 넘어간 뒤 옛 키를 `TrustedKeys`와 허용 목록에서 뺍니다.

키가 이미 유출된 경우에는 기다리지 않습니다. 새 키만 넣은 버전을 각 약국에 직접 설치합니다.

## 권장 (GitHub 설정 — 소유자가 직접)

- **보호 규칙:** `main` 브랜치에 보호 규칙(리뷰 필수)을 겁니다. `internal/updater`, `tools/relsign`, `Makefile`, `frontend/package*.json`, `vite.config.ts`에는 CODEOWNERS로 소유자 리뷰를 겁니다.
- **다른 사람이 바꾼 코드를 돌릴 때:** `go test`, `npm install`, 빌드가 모두 해당합니다. 이런 코드는 같은 사용자 권한으로 비밀 키 파일을 읽을 수 있습니다. 외부 기여(PR)는 읽어 본 뒤에 실행합니다.
- 더 강하게 지키려면 비밀 키를 별도 사용자 계정이나 하드웨어 키에 둡니다.
- 모든 팀원은 GitHub 2단계 인증(MFA)을 켭니다.

## 업데이트·오류 보고 (토큰 불필요)

이 저장소는 공개 저장소입니다. 앱은 토큰 없이 릴리스를 확인·설치하고, 오류 보고는 브라우저의 GitHub 새 이슈 창을 엽니다. 사용자가 내용을 확인한 뒤 직접 올리며, 보고에는 거래 자료가 들어가지 않고 경로·파일 이름이 가려집니다.

- 설정 → 업데이트의 '저장소'를 바꾸면 다른 포크(fork)의 릴리스를 받을 수 있습니다. 그 저장소의 서명 키로 서명된 파일만 설치되므로, 포크를 배포하려면 자기 키로 앱을 빌드해야 합니다.
- 비공개 포크에서 쓰려면 설정에 그 저장소의 읽기 전용 토큰을 넣습니다.
